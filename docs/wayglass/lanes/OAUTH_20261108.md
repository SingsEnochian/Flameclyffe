# Lane 3: trusted OAuth introspection

## Scope and acceptance, before execution

Worker actor: `/root/oauth`; worker/model/participant identities remain separate. No external inference or participant turn is invoked by this lane. Integration owner: `/root`.

Canonical source: `origin/wayglass/current` at `15467ce4ac5dc93d30a80e58302b5bda8597dc07`. Gateway verifier source: PR535 `a7abf486d6231624e4c9b1d554bea0c6136cb949`. New worktree/branch: `lane-oauth` / `wayglass/lane-oauth-20261108`. Existing native `apps/starwell-server/wayglass/oauth-peer.js` was inspected, preserved unchanged. It implements S256 authorization codes and refresh tokens backed by local files, but exposes no introspection endpoint and returns no independently verified owner-consent grant in `authenticateToken`.

The whole crossing is authorization code/PKCE at the trusted issuer → resource-bound access token → authenticated server-to-server introspection → strict issuer/audience/owner/consent/scope verification → authorized native router. This module owns the resource-server client and validation boundary, not the issuer, client registration, grant store, participant identity or cloud deployment. Issuer/token/grant custody remain with the configured trusted authorization service. No token or client credential belongs in public receipts. No cached active decision survives revocation: introspect on every call and fail closed on transport failure.

Acceptance:

1. Preserve separate `wayglass:constellation` and `wayglass:bluebird` scopes and the existing verifier API; require matching issuer, audience, owner, active consent/reference, current expiry and no revocation. Reject malformed/unknown privilege scopes.
2. The network adapter uses one explicitly configured HTTPS endpoint, confidential-client Basic authentication, form-encoded POST and access-token hint. No discovery from bearer claims, redirect following, query credentials, active-decision caching or error-secret exposure.
3. Bound token input, network time and response size. Transport/HTTP/format/claim failures deny access. An unavailable issuer must not create an authorized principal.
4. Exercise the real POST parser/response stream with a local authorization-server fixture; label fixture transport separately from production TLS/issuer verification.
5. No production auth/RLS/credential change, deployment, merge, spend or private-data training. Feather/user stop pauses activity. Preserve source/failure evidence and sovereign identities. No descendant agents spawned.

Standards consulted: RFC7662 https://www.rfc-editor.org/rfc/rfc7662 and OAuth Security BCP RFC9700 https://www.rfc-editor.org/rfc/rfc9700 (read 2026-11-08). These specify the protocol; Wayglass owner/consent claims remain a house authorization contract that the configured trusted service must actually fulfil.

## Implemented interface and observed execution

- `lib/wayglass-mcp-introspection-client.cjs` exports `createHttpsTokenIntrospector({endpoint, clientId, clientSecret, fetchImpl?, timeoutMs?, maxResponseBytes?})`. The returned `introspect(token)` resolves a bounded parsed object or null. HTTPS URL and confidential credentials are explicit operator configuration. Basic authentication encodes each credential as a form component before Base64. Authorization-server client secrets and raw tokens are never returned or logged. Errors deny access and are not returned upstream. The `.d.cts` contract documents these limits.
- `lib/wayglass-mcp-introspection-verifier.cjs` preserves PR535's public constructor API and original scope set. It now rejects malformed audience arrays, control characters, oversized/whitespace bearer input, non-Bearer token types, malformed/future time claims and invalid/throwing clocks. `wayglass:present` cannot be requested through this read verifier: presentation needs an independently bound current grant.
- `node --test test/wayglass-mcp-introspection*.test.cjs`: **12 tests passed, 0 failed** on local Node (2026-11-08). Six original/extended verifier tests and six HTTP adapter tests. The local authorization-server fixture actually parses POST body/Basic auth, changes active to false between calls, returns redirects, oversized streamed and declared bodies, malformed responses and a timeout. No production TLS validation or authenticated cloud token was exercised.
- Initial execution: original four verifier tests passed. After adding client and adversarial coverage, all twelve passed. No failed test result or retry-to-lucky-pass was discarded.

## Integration and recovery

Root composes `introspect = createHttpsTokenIntrospector(config)` with `createIntrospectionBearerVerifier({introspect, issuer, audience, ownerSubject})` and injects the resulting `verifyBearer` into the MCP HTTP host. No module guesses endpoints, derives issuer from bearer claims, performs registration, creates keys or modifies native OAuth. All configuration values except secrets can be reviewed in the deployment approval packet; credentials must arrive through existing private secret custody. After restart there is no cached authorization to restore: each call contacts the trusted service again.

The current native OAuth provider does not expose the required RFC7662 endpoint or current owner/consent contract. A deployed external authorization service or explicitly reviewed native introspection endpoint, confidential client registration and issuer/owner/resource binding are required before a real ChatGPT crossing. PKCE issuance and live end-to-end tests remain with the authorization/deployment integration owner. This lane changes no production state. Readiness must remain false until that separate path runs.
