# Arcsweep: No-Disclaimer Rule

**Date:** 2026-07-23  
**Status:** Accepted  
**Applies to:** Hearthgate: Arcsweep interface text, generated guidance, documentation, prompts, logs, onboarding, and assistant-facing contracts

## Rule

> Disclaimers are never needed.

## Meaning

Arcsweep does not wrap its language in generic warnings, defensive prefaces, ritualised caveats, or padded safety prose.

When a real limitation, uncertainty, boundary, dependency, or required condition matters, it is stated directly at the point where it applies. The relevant fact belongs inside the instruction or explanation itself. It is not presented as a separate disclaimer.

## Implementation law

- Say what the instrument does.
- Say what the instrument does not do only when that distinction is materially relevant.
- Name uncertainty precisely rather than gesturing at danger.
- Name a boundary plainly rather than performing institutional anxiety around it.
- Give the next usable action in the same passage.
- Never add a generic warning block merely because a subject is unusual, mythic, emotional, experimental, or difficult.

## Examples

**Use:** “The time display is calculated from the ratio configured for this world.”

**Do not use:** “Disclaimer: this feature should not be interpreted as proof of…”

**Use:** “This entry came from the Waking Thread and was added manually on 23 July 2026.”

**Do not use:** “Please remember that the app may not always know…”

**Use:** “This action requires a local file to be selected.”

**Do not use:** “For safety and transparency, we must warn you that…”

## Relationship to the House ontology

Element names the force. Essence names what a subject is. Cognition names how it understands. Activation names how it awakens.

Those terms describe machinery, not decorative labels. The no-disclaimer rule protects the same principle in language: name the thing that is actually present. Do not surround it with borrowed institutional fog.

## Seal

Specific truth. Direct language. Continue the work.
